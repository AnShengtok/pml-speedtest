# 测速取值规范 v1

定稿日期：2026-09-11 ｜ 适用：公网网页端 / PC 原生端 / 安卓端（三端同源 `pml/web/assets/index.html`）
本规范是「取值口径 + 测速形态 + 单位」的唯一裁决书。任何一端与本文件冲突，以本文件为准并回改代码。

## 1. 结论速览

- 形态：**统一采用两段式**（先下行、后上行），打流模式仍为并发饱和。
- 取值：**下行取「下行阶段 1s 窗口中位数」，上行取「上行阶段 2s 窗口最大值」**，弹窗值 = 上报值 = 同一个变量，禁止两套口径。
- 单位：内部一律 **Mbps（十进制 1e6 bit/s）**，显示层换算，1 MB/s = 8 Mbps，默认 Mbps。
- 三端精度：PC 原生与网页浏览器读数已收敛到 **5% 以内**，且上行以 PC 原生更稳定 → 口径按本文件统一，不各测各的。

## 2. 测速形态（D1 定稿）

| 模式 | 行为 | 实现位置 |
|---|---|---|
| 测速（speedtest） | 下行 10s → 停止并结算 → 上行 10s → 停止并结算 → 弹窗 | `ST_SEQ` 状态机 |
| 打流（sustain） | 按所选方向并发持续，随时可停，不弹窗 | `brSpawnConcurrent` / `engineStart(mode,0)` |

关键事实：**两段式由前端统一驱动，原生引擎不需要自己排阶段**。

- 浏览器引擎：`beginRun()` → `brRunPhase("download",DL_SEC)` → `brAdvance()` → `brRunPhase("upload",UL_SEC)` → `browserFinalize()`
- 原生引擎：`nativeStart()` → `engineStart("download",DL_SEC,onDownPhase)` → `onDownPhase()` → `engineStart("upload",UL_SEC,onUpPhase)` → `onUpPhase()` → `nativeFinalize()`

所以「把网页形态同步到 PC」的正确做法是**重编 PC 让内嵌页跟上同源前端**，而不是在 Go 里再写一套阶段机。（本次已完成：`pml-pc-new.exe` md5 `c0e7c8a4`。）

## 3. 取值口径（D2 定稿）

| 指标 | 口径 | 代码 | 为什么这么取 |
|---|---|---|---|
| 结果·下行 | 下行阶段各 1s 窗口速率的**中位数** | `median(sdlS)` | 抗 CDN 单点抽风与末段衰减；实测比峰值稳（raw 峰 628.5 vs 中位 527.3） |
| 结果·上行 | 上行阶段各 2s 窗口速率的**最大值** | `max(sulS)` | 上行受拥塞窗口影响强，中位会把爬坡段算进来压低结果；2s 窗已滤掉毛刺 |
| 窗口速率 | 滑动窗内**已确认字节**×8×OH / 实际跨度 | `winMbps()`，`OH=1.06` | 窗口法避免「总字节/总用时」把 ramp 与停顿平摊 |
| 峰值卡 | 阶段内窗口最大值 | `peakDl/peakUl` | 只作观察，不作结果 |
| 平均吞吐 | 总字节×8 / 总用时 | `lastAvg` | 打流模式的主读数 |
| 实时曲线 | 瞬时 EMA（升 0.55 / 降 0.22）+ 大跳跃短路 | `p0seq()` | 平滑但不错过真实跃迁 |
| 上报后台 | **与弹窗同一变量** | `report("test",{peakDl:RES_DL,...})` | 杜绝「弹窗一套、后台一套」 |

硬性约束（踩过的坑）：

1. **上行字节必须是实发确认**：同源 `/ul` 走服务端响应确认，第三方 CDN 走 `xhr.upload.onprogress`。把发送缓冲当作已上传 = 之前「上行 1000 Mbps」假数据的根因。
2. `maxMbps` 入库上限 2000 Mbps，回环/内网来源直接 403。
3. 阶段切换后 1s 宽限期不出数（`GRACE_MS`），避免上一阶段尾巴污染下一阶段。

## 4. 单位规范（§7.1 定稿）

- 存储与计算：**永远 Mbps**，十进制 `1e6`；`OH=1.06` 是窗口法对 TCP 慢启动的实测补偿，保留。
- 显示：`fmt(mbps)` 是唯一出口，按 `UNIT` 换算；坐标轴 `fmtAxis(v)` 同源。
- 一致性：仪表盘、实时指标卡、结果弹窗、历史列表、页脚、复制文本 **全部走 `fmt()`**，DOM 单位标签用 `data-unit` 由 `applyUnit()` 统一刷新。
- 持久化：`localStorage["pml_ls_v2"].unit`；`clearStats()` 清统计但**保留单位偏好**。
- 有效位：Mbps 固定 1 位小数；MB/s 按量级 2/1/0 位小数。
- 不换算的例外：网口协商速率（`showConns`）恒为 Mbps，属链路能力而非吞吐。

## 5. 跨阶段累计（今晚修复的口径漏洞）

原生引擎每阶段计数器独立，且 SSE `tick` 会把 `startT` 重基到当前阶段，导致两段式测速：

- 用时只算了最后一段（报 10s，实际 20s+）
- 共传只保留最后一段（上行段的 73.8 MB），下行 4 亿字节丢失 → **后台「消耗」列与今日流量对 PC/APK 严重低估**

修复：`engineStopOnly()` 累计 `final.seconds/dl_bytes/ul_bytes` 到 `ST_SEC/ST_BDL/ST_BUL`，`onUpPhase()` 与手动停止都用累计值结算。实测：用时 10s→23s，共传 73.8 MB→481.4 MB。

## 6. 三端实测对比（同一台机器，1 分钟内交替）

机器：以太网 1000 Mbps，出口 China Mobile 杭州，测速页为公网部署版。

| 轮次 | 引擎 | 下行 | 上行 | 用时 | 共传 |
|---|---|---|---|---|---|
| R1 | PC 原生 | 374.8 | 45.8 | 修复前 10s | 修复前 73.8 MB |
| R1 | 网页浏览器 | 367.4 | 39.5 | 20s | 408.7 MB |
| R2 | PC 原生 | 407.0 | 44.8 | 修复前 10s | 修复前 72.4 MB |
| R2 | 网页浏览器 | 358.2 | 31.0 | 20s | 431.0 MB |
| R3 | PC 原生（修复后） | 387.4 | 45.7 | 23s | 481.4 MB |
| R3 | 网页浏览器 | 370.5 | 43.4 | 20s | 498.1 MB |

判读：

- **修复后两端下行差 4.4%（387.4 vs 370.5）、上行差 5.1%（45.7 vs 43.4）**，属同一次真实带宽的正常抖动，判定「同一口径下三端可比」。
- 上行稳定性：PC 原生 44.8/45.7/45.8（极差 1.0），网页 31.0/39.5/43.4（极差 12.4）。原生更稳，因为 Go 引擎按 socket 实发计数，浏览器受 CDN 端点接受度影响。
- 结论：**保留网页的统计口径（中位/2s 峰值），但字节来源以「服务端或实发确认」为准**；APK 与 PC 共用原生引擎，天然满足。
- 外部基准 `speedtest.im` 本机出口 IP 为比利时（海外流量走代理），路径不可比，**不作为定标依据**；如需外部对照，应改用境内同源基准或在无代理出口时复测。

## 7. 验收红线

1. 取值/调度类改动：改 → 重编 → 真机跑一轮 → 记录 用时/共传/下/上 四元组，才允许合主干。
2. 每轮至少 2 次交替 A/B 复测，避免把网络抖动当改进。
3. 手动停止**不得**弹测速结果（`manual` 标志），只有自然完成才弹。
4. 一次测速在后台只新增 1 行 `test`（阶段中途不上报）。
